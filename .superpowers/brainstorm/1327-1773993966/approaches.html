Protocol Plugin Architecture — Three Approaches

Click the approach you prefer, or respond in terminal

A

Recursive Protocol Tree

Recommended — Matches your original vision

TCP (root)
├── HTTP/1.x  ← canMatch("GET ", "POST"...)
├── TLS  ← canMatch(0x16 ClientHello)
│   ├── HTTP/1.x  ← same plugin, different parent
│   ├── HTTP/2  ← ALPN "h2"
│   └── WebSocket  ← Upgrade header
├── SOCKS5  ← canMatch(0x05)
│   └── → re-enter TCP subtree
└── MQTT, Redis...

UDP (root)
├── DNS  ← port 53 or header match
├── QUIC  ← canMatch(Long/Short Header)
│   └── HTTP/3
└── NTP  ← port 123

Pros

  • Directly models the protocol hierarchy
  • Parent-child relationship explicit in code
  • Easy to add new leaf protocols
  • Framework handles match→dispatch recursion

Cons

  • TLS/SOCKS5 need async "re-detect" (handshake first)
  • Same plugin at multiple tree positions needs careful identity
B

Event-Driven Plugin Chain

Plugins emit events, central dispatcher routes

Connection in → Dispatcher tries all plugins
→ TLS matches → emits .decrypted event
→ Dispatcher tries all plugins again on decrypted bytes
→ HTTP matches → emits .httpRequest event
→ Recorder picks up events

Pros

  • Very flexible, plugins fully decoupled
  • No tree structure to maintain
  • Natural async (events are inherently async)

Cons

  • Hard to reason about — who handles what?
  • No explicit parent-child, ordering is implicit
  • Debugging event chains is painful
  • Over-engineered for a single app
C

Layered Pipeline Stages

Each protocol is a composable transform stage

bytes → [TCP Stage] → [TLS Stage] → [HTTP Stage]
                                └→ [gRPC Stage]

Each stage: input bytes → transform → output bytes/messages

Pros

  • Mirrors what NIO pipeline already does
  • Each stage is a pure transform
  • Composable

Cons

  • Essentially re-inventing NIO's ChannelPipeline
  • Detection logic doesn't fit the "stage" model
  • Doesn't add structure beyond what NIO provides
