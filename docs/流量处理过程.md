# Knot 流量处理全流程详解

## 总览架构图

系统存在两条**并行的捕获路径**：传输层（数据包级别）和应用层（协议/流级别），通过 `flow_id` 关联。

```mermaid
flowchart TD
    NET[网络流量] --> VPN[NEPacketTunnelProvider<br/>VPN 隧道入口]

    VPN --> PATH1[路径1: 传输层捕获<br/>每个 IP 包]
    VPN -->|TCP 流量重定向到本地代理| PATH2[路径2: 应用层捕获<br/>每个请求/响应]

    PATH1 --> PCE[PacketCaptureEngine]
    PCE --> IPP[IPPacketParser<br/>解析 IP/TCP/UDP/ICMP 头]
    IPP --> BW[BatchWriter<br/>批量累积 50条 或 0.1s 刷写]
    BW --> TDB1[(transport.db<br/>packet 表)]

    PATH2 --> PS[ProxyServer 监听端口<br/>Master: coreCount 线程<br/>Worker: coreCount×3 线程]
    PS --> C{ProtocolRouter<br/>检查前 4 字节判断协议类型}

    C -->|"GET/POST/PUT/HEAD 等"| D[HTTP 明文]
    C -->|"CONN (CONNECT)"| E[HTTPS 隧道请求]
    C -->|"0x16 0x03 (TLS ClientHello)"| F[直连 TLS]
    C -->|其他| G[RAW 未知协议]

    D --> D1[HTTPCaptureHandler]
    E --> E1[ConnectHandler]
    F --> F1[TunnelHandler]
    G --> G1[RawPassthroughHandler]

    E1 -->|回复 200 Connection Established| E2{规则匹配决策}
    E2 -->|拦截 MITM| E3[MITMHandler<br/>动态生成证书 + TLS握手]
    E2 -->|透传 Passthrough| E4[TunnelHandler<br/>+ TLSSniffHandler 被动嗅探]

    E3 --> E5{ALPN 协商}
    E5 -->|h2| E6[HTTP2CaptureHandler]
    E5 -->|http/1.1| E7[HTTPCaptureHandler]

    E6 --> E8{检测 content-type}
    E8 -->|application/grpc| E9[GRPCCaptureHandler]
    E8 -->|其他| E10[普通 HTTP/2 处理]

    D1 --> SR[SessionRecorder<br/>中央记录器]
    E7 --> SR
    E6 --> SR
    E9 --> SR
    E4 --> SR
    F1 --> SR
    G1 --> SR

    SR --> DB[(TaskDatabaseGroup<br/>protocol.db / connection.db<br/>decoded.db / state.db)]
    SR --> PW[PayloadWriter<br/>请求/响应体文件]

    TDB1 -.->|flow_id 关联| DB
```

## 传输层：数据包捕获（路径1）

这是一条**独立于代理层的底层捕获路径**，在 VPN 隧道入口处捕获所有原始 IP 包。

### 捕获流程

```mermaid
flowchart TD
    A[NEPacketTunnelProvider] -->|packetFlow.readPackets| B[PacketCaptureEngine]
    B --> C[IPPacketParser]

    C --> C1{传输协议?}
    C1 -->|TCP| D1[解析 TCP 头<br/>seq/ack/flags/window]
    C1 -->|UDP| D2[解析 UDP 头<br/>src_port/dst_port/length]
    C1 -->|ICMP| D3[解析 ICMP 头<br/>type/code]

    D1 --> E[CapturedPacket]
    D2 --> E
    D3 --> E

    E --> F[PacketCaptureDelegate<br/>.didCapturePacket]
    F --> G[BatchWriter<br/>累积 50 条 或 0.1s 超时]
    G -->|insertBatch 事务写入| H[(transport.db<br/>packet 表)]

    B -->|同时| PCW[PCAPWriter<br/>可选导出 .pcap 文件]

    subgraph UDP分流["UDP 特殊处理"]
        D2 --> U1{端口判断}
        U1 -->|53| U2[DNS 查询<br/>→ DNSRecorder]
        U1 -->|443| U3[QUIC 连接<br/>→ QUICMITMManager]
        U1 -->|123| U4[NTP 等<br/>→ UDPForwarder]
    end
```

### 入口文件

| 平台 | 文件 |
|-----|------|
| macOS | `SystemExtension-macOS/MacPacketTunnelProvider.swift` |
| iOS | `PacketTunnel-iOS/PacketTunnelProvider.swift` |

### packet 表结构

| 字段 | 类型 | 说明 |
|-----|------|------|
| id | INTEGER PK | 自增主键 |
| flow_id | TEXT | 关联应用层 flow 记录 |
| direction | INTEGER | 入站/出站 |
| timestamp | REAL | 捕获时间 |
| ip_version | INTEGER | 4 或 6 |
| src_ip / dst_ip | TEXT | 源/目标 IP |
| transport | INTEGER | 6=TCP, 17=UDP, 1=ICMP |
| src_port / dst_port | INTEGER | 源/目标端口 |
| seq_no / ack_no | INTEGER | TCP 序列号/确认号 |
| tcp_flags | INTEGER | TCP 标志位 (SYN/ACK/FIN 等) |
| window_size | INTEGER | TCP 窗口大小 |
| payload_length | INTEGER | 负载长度 |
| payload_ref | TEXT | 负载文件引用 |

### 写入机制

- **BatchWriter**: 累积到 **50 条**或超时 **0.1 秒**自动 flush，在事务中批量 INSERT
- 使用独立的 serial DispatchQueue 保证线程安全，避免 SQLite BUSY

### 两条路径的关系

```mermaid
flowchart LR

        P5[packet 5: HTTP 200]

    end

    subgraph 应用层["应用层 (protocol.db)"]
        F1[flow: GET /api/users → 200<br/>1 条记录]
    end

    P1 -.->|flow_id| F1
    P2 -.->|flow_id| F1
    P3 -.->|flow_id| F1
    P4 -.->|flow_id| F1
    P5 -.->|flow_id| F1
    P6 -.->|flow_id| F1
    P7 -.->|flow_id| F1
```

| 对比维度 | 传输层 (packet) | 应用层 (flow) |
|---------|----------------|--------------|
| 数据库 | transport.db | protocol.db |
| 粒度 | 每个 IP 包一条记录 | 每个请求/响应一条记录 |
| 捕获位置 | VPN 隧道入口 (NEPacketTunnelProvider) | 本地代理 (ProxyServer) |
| 内容 | IP/TCP/UDP 头、包长、时序 | method、URI、headers、status、decoded payload |
| 协议覆盖 | 所有 IP 流量 (TCP/UDP/ICMP) | HTTP、HTTPS、WebSocket、gRPC、DNS |
| 关联方式 | flow_id 字段 | flow_id 字段 |

> **当前状态**: Schema、DAO、BatchWriter、Parser 均已实现，但 `PacketCaptureEngine` → `PacketDAO` 的调用尚未接通，属于 Phase 3 计划任务。

## 应用层：协议捕获（路径2）

以下为应用层代理管线的详细处理过程。

## 第1层：ProtocolRouter — 协议路由

**文件**: `Proxy/ProtocolRouter.swift`

| 检测特征 | 判定协议 | 走向 |
|---------|---------|------|
| `GET ` / `POST` / `PUT` / `HEAD` 等 | HTTP 明文 | → `configureHTTPPipeline()` |
| `CONN` (HTTP CONNECT) | HTTPS 隧道请求 | → `configureHTTPSPipeline()` |
| `0x16 0x03 xx xx` (TLS ClientHello) | 直连 TLS | → `configureTunnelPipeline()` |
| 其他 | 未知/RAW | → `configureRawPipeline()` |

**职责**: 读取连接的前几个字节，决定后续 pipeline 该装哪些 Handler。

---

## 第2层：协议处理器（四条主线）

### 主线1: HTTP 明文

```mermaid
sequenceDiagram
    participant Client
    participant HTTPCaptureHandler
    participant SessionRecorder
    participant Server as 真实服务器
    participant ResponseRelayHandler

    Client->>HTTPCaptureHandler: HTTP 请求 (GET /api/users)
    HTTPCaptureHandler->>SessionRecorder: recordRequestHead()
    HTTPCaptureHandler->>SessionRecorder: recordRequestBody() (流式)
    HTTPCaptureHandler->>Server: 建立连接 + 转发请求
    Server->>ResponseRelayHandler: HTTP 响应
    ResponseRelayHandler->>SessionRecorder: recordResponseHead()
    ResponseRelayHandler->>SessionRecorder: recordResponseBody() (流式)
    ResponseRelayHandler->>HTTPCaptureHandler: 回传响应
    HTTPCaptureHandler->>Client: 响应数据
```

**HTTPCaptureHandler** 干的活：
- 接收客户端 HTTP 请求
- 调用 `SessionRecorder.recordRequestHead()` 记录请求头
- 调用 `SessionRecorder.recordRequestBody()` 流式写入请求体
- 通过 `ClientBootstrap` 连接真实服务器，转发请求
- 通过 `ResponseRelayHandler` 接收服务器响应
- 调用 `recordResponseHead()` / `recordResponseBody()` / `recordResponseEnd()`
- 将响应回传给客户端

### 主线2: HTTPS 隧道

```mermaid
flowchart TD
    A[Client 发送 CONNECT host:443] --> B[ConnectHandler]
    B -->|回复 200 Connection Established| C{规则匹配}

    C -->|拦截| D[MITMHandler]
    C -->|透传| E[TunnelHandler]

    D --> D1[动态生成目标域名证书]
    D1 --> D2[与客户端完成 TLS 握手]
    D2 --> D3{ALPN 协商}
    D3 -->|h2| D4[HTTP/2 Pipeline<br/>HTTP2CaptureBuilder]
    D3 -->|http/1.1| D5[HTTP/1.1 Pipeline<br/>HTTPCaptureHandler]

    E --> E1[TLSClientSniffHandler<br/>解析 ClientHello]
    E1 -->|提取 SNI/CipherSuites/ALPN| E2[数据原样透传]
    E2 --> E3[TLSServerSniffHandler<br/>解析 ServerHello]
    E3 -->|提取证书链/选中密码套件| E4[TunnelRelayHandler<br/>双向透传]

    E1 -.->|嗅探后自移除| E1X((×))
    E3 -.->|嗅探后自移除| E3X((×))
```

**ConnectHandler**: 处理 CONNECT 请求，根据规则引擎决定是 MITM 拦截还是透传

**MITMHandler**:
- 用 CA 证书动态签发目标域名的证书
- 与客户端完成 TLS 握手（客户端以为在跟真实服务器通信）
- ALPN 协商后分流到 HTTP/1.1 或 HTTP/2 管线

**TLSSniffHandler** (透传模式下的被动嗅探):
- `TLSClientSniffHandler`: 解析 ClientHello → 提取 SNI、密码套件列表、ALPN
- `TLSServerSniffHandler`: 解析 ServerHello → 提取选中的密码套件、证书链
- **不修改任何数据**，只读取元数据后自行移除

### 主线3: 直连 TLS

直接走 `TunnelHandler`，类似 HTTPS 透传模式。

### 主线4: RAW 未知协议

`RawPassthroughHandler`: 记录前几个字节作为样本，创建最小化的 FlowRecord，数据原样透传。

## 第3层：SessionRecorder — 中央记录器

**文件**: `Storage/Proxy/SessionRecorder.swift`

**每个连接创建一个 SessionRecorder**，它是所有数据记录的中枢：

```mermaid
flowchart TD
    SR[SessionRecorder] --> FID[生成唯一 FlowId]
    SR --> TDB[打开 TaskDatabaseGroup<br/>按需 / 引用计数]
    SR --> PR[创建 ProtocolRecorder<br/>HTTP / WebSocket / gRPC / DNS]
    SR --> PW1[PayloadWriter - 请求体]
    SR --> PW2[PayloadWriter - 响应体]
    SR --> TM[记录连接时序]

    TM --> T1[connect_at — 开始连接]
    TM --> T2[connected_at — TCP 连接建立]
    TM --> T3[tls_done_at — TLS 握手完成]
    TM --> T4[req_end_at — 请求发送完毕]
    TM --> T5[rsp_start_at — 收到第一个响应字节]
    TM --> T6[ended_at — 连接关闭]
```

## 第4层：协议特化记录器

```mermaid
flowchart TD
    PR[ProtocolRecorder 协议接口] --> HTTP[HTTPRecorder]
    PR --> WS[WebSocketRecorder]
    PR --> GRPC[GRPCRecorder]
    PR --> DNS[DNSRecorder]
```

| 记录器 | 记录内容 | 搜索键 |
|-------|---------|-------|
| **HTTPRecorder** | method, uri, status, headers, timing | key1=method, key2=uri, key3=statusCode, key4=contentType |
| **WebSocketRecorder** | 帧数量、帧方向、帧类型、close code | key1=subprotocol, key2=uri, key3=totalFrames, key4=closeCode |
| **GRPCRecorder** | service, method, grpc status, 请求/响应 messages | key1=method, key2=service, key3=grpcStatus, key4=grpcMessage |
| **DNSRecorder** | query domain, type, response code, answers | key1=queryType, key2=domain, key3=firstAnswer, key4=responseCode |

**GRPCRecorder 特殊行为**: 初始化时就做一次 **preliminary insert**（安全插入），确保即使连接中途断开也有记录。

### 谁在什么时候写了什么

| 时机 | 写入目标 | 写入内容 | 捕获路径 |
|-----|---------|---------|---------|
| 每个 IP 包到达 | `BatchWriter` → transport.db | IP/TCP/UDP 头、seq/ack/flags、包长 | 路径1: 传输层 |
| 累积 50 条或 0.1s | `PacketDAO.insertBatch()` → transport.db | 批量事务写入 packet 表 | 路径1: 传输层 |
| 收到请求体 | `PayloadWriter` → 文件系统 | 请求 body 二进制流 | 路径2: 应用层 |
| 收到响应体 | `PayloadWriter` → 文件系统 | 响应 body 二进制流 | 路径2: 应用层 |
| gRPC 初始化 | `FlowDAO` → protocol.db | preliminary FlowRecord（防丢失） | 路径2: 应用层 |
| gRPC 每条消息 | `DecodedEntryDAO` → decoded.db | 单条 gRPC message | 路径2: 应用层 |
| WebSocket 每帧 | `DecodedEntryDAO` → decoded.db | 帧元数据 | 路径2: 应用层 |
| 连接关闭时 | `FlowDAO` → protocol.db | 完整 FlowRecord（最终版） | 路径2: 应用层 |
| 连接关闭时 | `TcpConnectionDAO` → connection.db | TCP 连接元数据 | 路径2: 应用层 |
| TLS 嗅探时 | FlowRecord metadata (JSON) | TLS SNI/密码套件/证书链 | 路径2: 应用层 |

**线程安全**: 每个数据库有独立的 serial DispatchQueue，所有写入都通过队列串行化。

## 一个完整 HTTP 请求的生命周期

```mermaid
sequenceDiagram
    participant Client
    participant Router as ProtocolRouter
    participant HCH as HTTPCaptureHandler
    participant SR as SessionRecorder
    participant PW as PayloadWriter
    participant Server as 真实服务器
    participant RRH as ResponseRelayHandler
    participant DB as protocol.db / connection.db

    Client->>Router: ① 连接到 Proxy 端口
    Router->>Router: 读前4字节: "GET " → HTTP
    Router->>HCH: ② configureHTTPPipeline()
    Router->>SR: 创建 SessionRecorder (生成 flowId)

    Client->>HCH: ③ GET /api/users HTTP/1.1
    HCH->>SR: recordRequestHead()<br/>内存记录 method/uri/headers/host

    Client->>HCH: ④ 请求体 (如果有)
    HCH->>PW: append() → {flowId}_req.bin<br/>uploadBytes += chunk.size

    HCH->>SR: ⑤ recordRequestEnd()<br/>关闭 PayloadWriter, 记录 req_end_at

    HCH->>Server: ⑥ 建立连接 + 转发请求<br/>记录 connect_at, connected_at

    Server->>RRH: ⑦ HTTP/1.1 200 OK
    RRH->>SR: recordResponseHead()<br/>记录 rsp_start_at

    Server->>RRH: ⑧ 响应体
    RRH->>PW: append() → {flowId}_rsp.bin<br/>downloadBytes += chunk.size

    RRH->>HCH: ⑨ 响应结束 → 回传给客户端
    HCH->>Client: 响应数据

    Note over SR,DB: ⑩ 连接关闭
    SR->>SR: HTTPRecorder.buildFlowRecord()<br/>summary="GET /api/users → 200"<br/>search_keys=["GET","/api/users","200","application/json"]
    SR->>DB: FlowDAO.insert() → protocol.db ✅
    SR->>DB: TcpConnectionDAO.insert() → connection.db ✅
    SR->>SR: 释放 TaskDatabaseGroup 引用
```

## 关键设计原则

1. **流式处理**: Payload 从不整体加载到内存，用 PayloadWriter 32KB 缓冲流式写入文件
2. **Fail-safe 写入**: gRPC 等长连接协议初始化就插入 preliminary record，防止中途断开丢数据
3. **引用计数**: TaskDatabaseGroup 通过引用计数管理生命周期，最后一个 SessionRecorder 关闭时才关库
4. **Pipeline 热切换**: WebSocket 升级时动态移除 HTTP Handler、装入 WS Handler，无需断开重连
5. **线程安全**: NIO Handler 运行在 EventLoop，数据库写入通过 serial DispatchQueue 串行化
6. **协议抽象**: `ProtocolRecorder` 统一接口生成 `FlowRecord`，`SearchKeyMapping` 提供协议特定搜索字段
